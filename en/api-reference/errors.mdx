---
title: "Errors"
description: "Use HTTP status, the returned request context, and a bounded recovery policy to handle failures."
---

Do not branch on error message prose. Store the HTTP status, model ID, timestamp, and request ID, then decide whether to fix, wait, or escalate.

## Status guide

| Status | Class | Action |
| --- | --- | --- |
| 400 / 422 | Invalid request | Validate the body and model-supported parameters; do not retry unchanged. |
| 401 | Authentication | Check that the server has the expected active key; do not expose it while debugging. |
| 402 | Account state | Check wallet or quota through the console; notify an operator. |
| 404 | Route or model | Use `/v1/models` to verify the model ID and check the request path. |
| 408 / 429 / 5xx | Transient | Use a small exponential-backoff retry budget, then surface a controlled failure. |

## Support context

- The HTTP status and response body after sensitive values have been removed.
- The exact model ID and the non-secret request configuration.
- The timestamp, request ID, and trace ID when the gateway returns them.
- Whether a retry or fallback was attempted and what outcome it had.
