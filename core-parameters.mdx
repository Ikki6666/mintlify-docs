<Tip>
  与模型交互时，可以通过调整不同的请求参数来控制模型的输出，以满足不同场景的需求。理解这些核心参数能帮助你更好地利用模型的能力。
</Tip>

## 快速参考

下表参数均用于 [Chat Completions](/api-reference/chat-completions) 请求体：

| 参数 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| [temperature](#temperature) | 浮点数 | 依赖模型 | 控制输出的随机性，值越高越随机 |
| [top_p](#top_p) | 浮点数 | 依赖模型 | 通过核采样控制多样性，建议与 `temperature` 二选一 |
| [max_tokens](#max_tokens) | 整数 | 依赖模型 | 限制单次调用生成的最大 token 数 |
| [max_completion_tokens](#max_completion_tokens) | 整数 | 依赖模型 | 部分模型使用的另一种输出 token 上限参数 |
| [stream](#stream) | 布尔值 | `false` | 是否以流式（SSE）方式返回响应 |
| [reasoning_effort](#reasoning_effort) | 字符串 | 依赖模型 | 控制推理模型的推理程度，仅声明支持该参数的模型可用 |

## 参数详解

### temperature

`temperature` 控制模型输出的随机性。

* 较低的值（如 `0.2`）：概率分布更「尖锐」，输出更确定、更保守。
* 较高的值（如 `0.8`）：概率分布更「平缓」，输出更随机、更多样。

最佳实践：

* 需要严谨、事实准确的场景（如知识问答），使用较低的 `temperature`。
* 需要创意的场景（如内容创作、头脑风暴），可以尝试较高的 `temperature`。
* 建议 `temperature` 和 `top_p` 只调整其中一个。

**注意**：功能型参数仅在模型声明支持时有效，调用前请先在[模型概览](/models)确认能力。

### top_p

`top_p`（核采样）通过限制采样的 token 概率范围来控制多样性。

* 较低的值（如 `0.2`）：缩小采样范围，输出更确定。
* 较高的值（如 `0.9`）：扩大采样范围，输出更多样。

最佳实践：

* 想在保证质量的同时获得一定多样性时，使用 `top_p`（推荐 `0.8`–`0.95`）。
* 通常不建议同时修改 `temperature` 和 `top_p`。

### max_tokens

`max_tokens` 限制模型单次调用生成的最大 token 数量，可以控制响应长度和成本。

* 限制的是**生成内容**的长度，不包括输入。
* 设置过小可能把回答截断；设置过大可能增加等待时间和成本。
* 部分模型使用 `max_completion_tokens` 作为另一种输出上限参数，效果相同。

Token 是文本的基本单位，可直观理解为「字」或「词」，具体换算比例因模型分词器而异。更多概念见下方[相关概念](#相关概念)。

当前推荐模型的最大输出：

| 模型 | 最大输出 |
| :--- | :--- |
| `glm-5.3` | 128K |
| `glm-5.2` | 256K |
| `glm-5-turbo` | 128K |
| `glm-4.7` | 128K |
| `glm-5.3-flash` | 128K |

各模型的每一档上限以[模型市场](http://maas.dev.origin-power.com/zh-CN/models)实时目录为准。

### stream

`stream` 控制 API 的响应方式。

* `false`（默认）：一次性返回完整响应，实现简单但等待时间长。
* `true`：以流式（SSE）方式增量返回内容，显著提升实时交互体验。

最佳实践：

* 聊天机器人、实时代码生成等界面型应用，建议设为 `true`。
* 后台批处理等无需实时反馈的场景，保持默认即可。

安全消费事件流的要点见[流式响应](/api-reference/chat-completions#流式响应)。

### reasoning_effort

`reasoning_effort` 控制推理模型开启思维链后的推理程度。

* 类型：字符串。
* 仅适用于支持参数中声明了 `reasoning_effort` 的推理模型。
* 可选值包括 `low`（轻量思考）、`high`（增强思考）、`max`（深度思考），各模型支持的具体取值可能不同。

最佳实践：

* 复杂推理、规划类任务使用较高档位。
* 简单任务使用较低档位，或换用非推理模型，以获得更快响应、更低成本。

## 相关概念

<AccordionGroup>
  <Accordion title="Token 用量计算">
    Token 是模型处理文本的基本单位，用量计算包括两部分：

    * **输入 Token 数**：发送给模型的文本所包含的 token 数量。
    * **输出 Token 数**：模型生成的文本所包含的 token 数量。
    * **总 Token 数**：输入与输出之和，是平台计费的依据。

    每次请求的实际消耗以响应中的 `usage` 字段为准（`prompt_tokens`、`completion_tokens`、`total_tokens`）。
  </Accordion>

  <Accordion title="最大输出 Tokens">
    最大输出 Tokens 是模型单次请求能够生成的最大 token 数量。

    它与 `max_tokens` 不同：`max_tokens` 是你在请求中主动设置的上限，而最大输出 Tokens 是模型本身的能力上限。`max_tokens` 设置得再大，也不会超过模型的最大输出。
  </Accordion>

  <Accordion title="上下文窗口">
    上下文窗口是模型一次请求能够处理的最大 token 长度，包括**输入文本**和**生成文本**的总和。

    * 输入与期望输出超过上下文窗口时，请求可能无法正常处理。
    * 不同模型的上下文窗口不同，长对话、长文档场景需要重点关注。

    各模型的上下文限制见[模型概览](/models)。
  </Accordion>

  <Accordion title="请求出错怎么办">
    参数不合法时会返回 `400` / `422` 错误；使用了模型不支持的参数（如对不支持工具调用的模型传入 `tools`）也会被拒绝。

    常见状态码与排查清单见[错误码](/faq/error-codes)。
  </Accordion>
</AccordionGroup>
